# AGENTS.md — 仓库规范与文档

*[English](AGENTS.md)*

这份文件讲这个仓库里每类话该放哪、那些地方怎么加载、规则怎么写、双语配对怎么运转。怎么改、怎么验，看 [development.md](development.md)。

## 层级模型

一个事实，一个归属。别处都链过去。

| 层级 | 放这里 | 不放这里 |
| --- | --- | --- |
| 根目录 [`AGENTS.md`](../AGENTS.md) | agent 每场会话都要的常驻规则，每条一行到三行，各链到归属文件 | 步骤、例子、从被链文件里抄来的任何东西 |
| 子目录 `AGENTS.md` | 只对这个目录成立的规则 | 根目录文件说过的规则 |
| [`docs/`](.) | 步骤、数据模型、用户指引、像这份一样的标准 | 决策理由，抄一份就开始烂 |
| [`.agents/skills/`](../.agents/skills/pre-push-checks/SKILL.md) | 只在一个场景用得上的步骤，描述对上了任务才加载 | 每场会话都需要的规则 |
| [`.agents/notes/`](../.agents/notes/README.md) | 决定为什么这样作、放弃了什么、代价是什么；状态看文件夹名 | 当前行为 |
| [`README.md`](../README.md) | 这个插件是什么、怎么装、接下来去哪 | 给 agent 的规则 |

预算，文字版：

| 文件 | 上限 |
| --- | --- |
| 根目录 `AGENTS.md` | 1,200 |
| 子目录 `AGENTS.md` | 400 |
| `docs/` 下每份文件 | 1,200 |
| `README.md` | 700 |

[`scripts/doc-budgets.json`](../scripts/doc-budgets.json) 说了算，压过这些兜底值。文件超上限：先把内容挪到它的家，再精简，最后才提上限，并在改动里说明为什么。

## 双语文档

英文是唯一源头。每份文件都有两份，并排放着；中文那份是译文，绝不是第二份原文。

- **命名。** `docs/usage.md` 配 `docs/usage_zh.md`。后缀是 `_zh`，目录和主文件名都一样。
- **互相链接。** 两份文件的开头都链到对方，读者一眼落到自己要的语言，改的人也能找到配对。
- **一次提交。** 先改英文，提交前更新中文版。两份对不齐比只有一种语言更糟：读者信的是错的那份。
- **翻译，不重写。** 译文照着中文的习惯组织，不逐词对应。读起来像英文翻过来的中文——的字的堆积、能用动词偏用「被」、名词前垫「进行」「作出」、之一、一串「和」——是缺陷，不是风格选择。
- **时效。** 英文那份后改过、中文没跟上，`npm run check` 就把这一对标为过期。把受影响那段重译；要分几批改，先把文件记进 [`doc-budgets.json`](../scripts/doc-budgets.json) 的 `pendingTranslations`，改完删掉。
- **内容一致。** 例子、表格、错误文案、代码原样不动，只换行文。中文版带了英文版没有的事实，两份都是 bug。
- **例外。** `CHANGELOG.md` 和 `RELEASE_NOTES.md` 没有中文版：它们是只增不改的历史，译过的变更日志会跟它描述的提交脱节。清单在 [`doc-budgets.json`](../scripts/doc-budgets.json)。

配对少一份、两份不互相链接、任一文件超预算、中文比英文旧，`npm run check` 都报错。忘了译中文的那份会让构建失败，不会悄悄放到过期。

## 指令怎么加载

harness 自动加载最近的指令文件，从宽到细，去重，还有字节预算，超了先丢更宽的那些。两个后果：

1. 别为了显眼把一条规则跨层级抄。抄一遍花双倍预算，还造出两个会各自漂移的事实。
2. 规则放得越深越好，只要还用得上它的人都能读到。

## 规则怎么写

- **用祈使句，一个分句，加粗开头。** 扫读的 agent 找的是加粗那句，细节跟在后面的句子里。
- **触发条件和动作都写明。** 「改了 plan builder 就跑自测」胜过「保持测试绿着」。
- **带上理由或链接。** 长篇大论的理由写进决策记录，链过去。
- **写当前行为。** 历史归 git 和决策记录。
- **别抄目录。** 文件清单、路由表归源头文件。
- **加粗要省着用。** 处处加粗等于没有加粗。

一条规则能留下，只因它改变了 agent 本来会做错的决定。

## 这些文件怎么维护

- **出过事就复查**：agent 做错了，补上缺的规则，删掉误导它的那条。
- **往下长。** 文件快到预算了，把整段挪进归属它的文件，原地留一行。
- **能删就删。** 过时的规则会主动教错东西。
- **配对、链接、新旧都用机器查。** `npm run check` 解析本地链接、标题锚点、预算、配对，以及每对文件谁后改的。
- **没人执行的规则只是建议。** 在规则里说清楚，或者认了只有复查能兜底。
- **违反规则，先当文档 bug 查。** agent 反复无视一条规则，是它写得含糊、埋得太深，或者别处有矛盾。

## 废话清单

提交前，拿这份清单过一遍任何指令文件：

- 重复的规则：搜一句特别的话；留一个家，其余链过去。
- 历史跑出了它该在的家：写当前事实，链到记录。
- 行文里的状态词（"implemented"、"planned"）：状态看代码和目录树。
- 手抄的目录：链到源头。
- 推理过程：留结论，删走过的路。
- 大段的文字墙：拆开，或者把细节降级。
- 加粗通胀：处处加粗等于没有加粗。
